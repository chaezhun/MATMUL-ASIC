# 16×16 행렬 곱셈 ASIC

> 데이터패스를 한 사이클도 멈추지 않는 고정소수점 행렬 곱셈 엔진.

SRAM 인터페이스 뒤에 붙는 16×16 고정소수점 행렬 곱셈기다. 외부 테스터가 두 입력
행렬을 온칩 SRAM에 써 넣고 시작 신호를 한 번 주면, 엔진이 `o_done`을 올릴 때 결과를
읽어 간다. 메모리 포트를 늘리지 않고 **사이클당 MAC 2회**를 뽑아냈고,
2,051 사이클 중 2,048 사이클을 가동해 파이프라인 버블을 남기지 않았다.

## 배경

`O = A × B`, 세 행렬 모두 16×16. 입력은 8비트 2의 보수 고정소수점이고 소수부 길이를
실행 시간에 지정한다(0~7). 출력은 32비트로 같은 소수부 길이를 가지므로, 누산 결과를
매번 다른 양만큼 잘라내야 한다.

주어진 것은 포트 목록뿐이고 모듈 내부는 전부 직접 작성했다. 정답 외에 가산점 조건이
두 개 있었다.

| 조건 | 배점 |
|---|---|
| 매 클럭 AMEM·BMEM을 읽어 곱셈기를 **쉬지 않고** 가동 | +2 |
| 위를 지키면서 **곱셈과 누산 사이에 파이프라인 레지스터** 삽입 | +5 |

즉 목표는 "정답을 낸다"가 아니라 "데이터패스를 한 번도 멈추지 않고 정답을 낸다"였다.

## 시스템 구성

| | |
|---|---|
| 연산 | `O = A × B`, 16×16 × 16×16 |
| 데이터 형식 | 입력 8비트 2의 보수, 출력 32비트, 소수부 길이 0~7 런타임 지정 |
| 메모리 | 동기식 SRAM 3개 (AMEM, BMEM, OMEM), 16비트 워드 |
| 중재 | 상태 신호 하나(`core_working`)로 테스터·코어 소유권 전환 |
| 파이프라인 | SRAM 읽기 1단 + 곱셈/누산 사이 레지스터 1단 |
| 규모 | 단일 모듈 294줄, 플립플롭 129개 |

```
       외부 테스터                          내부 코어
            |                                   |
            +-------- core_working = !o_done ---+
            |                                   |
      +-----v-----+   +-----------+   +---------v---------+
      | AMEM/BMEM |-->| 곱셈기 2  |-->| pipe_reg -> 누산기 |--> OMEM
      +-----------+   +-----------+   +-------------------+
```

## 설계

### 사이클당 2 MAC — 공짜로

메모리 맵이 16비트 SRAM 워드 하나에 8비트 값 두 개를 담는다. 각 메모리에서 워드
하나를 읽으면 피연산자 쌍이 두 개 나오므로, 내부 루프가 `k = 0..15`가 아니라
`0..7`이다. SRAM 포트도 읽기 횟수도 늘지 않는다. 병렬성이 이미 저장 형식 안에 있었다.

```verilog
pipe_reg <= ($signed(amem_dout[15:8]) * $signed(bmem_dout[15:8]))
          + ($signed(amem_dout[7:0])  * $signed(bmem_dout[7:0]));
```

### 출력 원소 사이에 버블 없음

흔한 구현은 원소가 끝날 때마다 누산기를 비우고 결과를 저장하느라 쉰다. 원소당
1사이클만 쉬어도 256사이클이 날아간다. 대신 같은 사이클에 세 가지가 겹친다.

- 누산기를 비운 뒤 더하는 대신, 새 원소의 첫 부분곱으로 **덮어쓴다**
- 목적지 주소는 한 루프 앞서 `addr_o_reg`에 붙잡아 뒀으므로 카운터가 먼저 넘어가도
  쓸 곳을 잃지 않는다
- 누산기가 덮이는 바로 그 사이클에, 덮이기 직전 값을 OMEM에 쓴다

### 2사이클 파이프라인 보정

SRAM 읽기가 1사이클, 파이프라인 레지스터가 1사이클을 더하므로 k=0에 요청한 피연산자의
곱은 k=2가 되어야 누산기에 도달한다. 상수 세 개가 이 어긋남을 흡수한다.

| 상수 | 이유 |
|---|---|
| `cnt_k == 2` 에 누산기 대입 | 새 원소의 첫 부분곱이 도착하는 시점 |
| `loop_cnt >= 1` 로 쓰기 차단 | 첫 워밍업 루프의 쓰레기값 억제 |
| `loop_cnt == 256 && cnt_k == 2` 에 종료 | 256번째 원소의 쓰기가 실제로 끝난 시점 |

하나라도 틀리면 전체 출력이 한 칸씩 밀린다.

### 중재와 읽기 경로

`core_working = !o_done` 하나로 SRAM 소유권을 외부 테스터와 내부 코어 사이에서
전환한다. 둘의 활동 구간이 겹치지 않으므로 핸드셰이크가 필요 없다. 테스터 쪽 경로에는
주소 상위 비트로 A/B/O를 고르는 디코더를 붙였다.

SRAM은 비활성 상태에서 X를 내보내는데, 사양은 인터페이스 미사용 시 `o_dout`이 0이어야
하고 A·B를 읽을 때는 상위 16비트가 0이어야 한다고 못박고 있다. 요청 포착과 출력 구동을
나눈 2단 읽기가 읽기 지연을 흡수하면서 두 요구를 **조건문이 아니라 데이터패스의
성질로** 만족시킨다.

## 결과

| | |
|---|---|
| 기능 | **정답 256 / 256 일치** (소수부 길이 4) |
| `o_done` 까지 사이클 | **2,051** — 유효 2,048 + 배출 3 |
| 곱셈기 가동률 | **99.85 %** |
| 연산 자원 | 8×8 곱셈기 2, 16비트 가산기 1, 32비트 누산기 1, 산술 시프터 1 |
| 상태 저장 | 플립플롭 129개 |
| 코드 | 294줄, 단일 모듈 |

워드에서 8비트씩 꺼내 쓰는 스칼라 구현이라면 4,096사이클이 필요하므로,
한 번의 읽기에 2 MAC을 접은 것이 그대로 2배다.

## 빌드와 실행

Vivado에서 설계를 top으로 두고 `provided/`를 시뮬레이션 세트에 추가한 뒤, 직접 작성한
`mm_tester`로 구동한다. 테스터 인터페이스로 `amem.hex`·`bmem.hex`를 적재하고
`i_matmul_en`을 한 번 펄스한 뒤 `o_done`을 기다렸다가 OMEM을 읽어 `omem_fl4.hex`와
비교하면 된다.

## 참고

**미포함** — `provided/`는 배포 파일로 수정할 수 없다. `tb_mm.sv`가 인스턴스화하는
`mm_tester`는 별도로 작성하는 모듈이라 제출 대상이 아니며 여기에도 포함하지 않았다.
